# Part 1 — Introduction · `[CORE]` · 預算 1:30

### 投影片 1-1：標題頁
**On slide：**
- **QAD-EDCA：Queue-Aware Dynamic EDCA**
- Dynamic EDCA Parameter Adaptation for Starvation Avoidance in IEEE 802.11 WLANs
- CSE625，NSYSU，Spring 2026

**Say (~10s)：**
> 大家好，我們這組做的是 802.11 EDCA 的飢餓問題：一個放在 AP 上的輕量控制器，在執行期偵測飢餓並調整 EDCA 參數。

---

### 投影片 1-2：研究動機——飢餓為何發生 `[CORE]`
**On slide：**
- 一條 Wi-Fi 同時承載 語音 / 視訊 / 網頁 / 背景同步
- EDCA 用**靜態**參數做優先級：VO > VI > BE > BK [1]
- 高負載下 **VO/VI 壟斷通道** → BE/BK 吞吐接近零 + 丟包過高 = **飢餓** [2][3]
- Wi-Fi 6/7（MU-EDCA、MLO）也還有這個問題 [10]
- **IEEE 802.11 沒有內建回饋機制**去偵測或修正飢餓

**Say (~35s)：**
> 現在的 Wi-Fi 同一條通道上同時跑語音、視訊、網頁、背景流量。EDCA 用四個優先級去區分，但這些參數是靜態的，連上之後就固定。負載一高，高優先級會一直搶到通道，低優先級的 BE、BK 就會被餓死，吞吐量幾乎是零、丟包很高——這是文獻已充分記載的（Ugwu et al. [2]、Mammeri et al. [3]）。這個問題到 Wi-Fi 6、7 都還在。關鍵在 IEEE 802.11 沒有回饋機制，沒有去偵測、也沒有去修正飢餓。我們要補的就是這一塊。

---

### 投影片 1-3：研究目標與貢獻 `[CORE]`
**On slide：**
- **QAD-EDCA**：AP 監控佇列 → 偵測飢餓 → 動態調 EDCA → 解除後指數衰減回復
- 目標：緩解飢餓 / 不用調參 / 不犧牲 VO/VI QoS / 複雜度 O(1)
- 貢獻：
  1. 形式化的飢餓判據（佇列 **OR** 丟包）
  2. 完整的 O(1) 閉迴路控制器
  3. 一個負面結果：穩態下回饋贏不過手調靜態，並解釋原因
  4. 對靜態與 DRL 的定位

**Say (~30s)：**
> 我們的方法叫 QAD-EDCA，只跑在 AP 上：每個 beacon 週期讀佇列狀態、判斷有沒有飢餓、調一下參數，沒事就慢慢調回預設。貢獻有四點，其中第三點是一個負面結果——穩態下這種回饋控制其實贏不過手動調好的靜態設定，我們會解釋為什麼會這樣。

# Part 2 — Background（精簡）+ 問題定義 · 預算 2:00

### 投影片 2-1：EDCA 預設值與飢餓問題（實測）`[CORE]`
**On slide：**
- IEEE 802.11-2020 預設值（OFDM PHY），CWmin/AIFSN 越低越容易搶到通道：

| AC | CWmin | AIFSN | TXOP |
|----|-------|-------|------|
| VO | 3 | 2 | 1.504 ms |
| VI | 7 | 2 | 3.008 ms |
| BE | 15 | 3 | 0 |
| BK | 15 | 7 | 0 |

- 實測（N=10，1VO/1VI/4BE/4BK）：標準 EDCA → **BE 丟包 ≈ 94.7%、延遲 ≈ 1086 ms**
- Ugwu et al. [2]：**AIFSN 對此差異的影響最大**
- Mammeri et al. [3] 提出 SDMA：**依賴通道綁定** — 不適用單通道 BSS

**Say (~45s)：**
> 先快速帶背景。這是標準 EDCA 的預設值 [1]，CWmin 跟 AIFSN 越小就越容易搶到通道，所以 VO、VI 會贏。下面是我們實際模擬的結果，N=10、四個 BE 飽和的情況下，標準 EDCA 的 BE 丟包率大概 94.7%、延遲超過一秒，基本上就是被餓死。文獻也一致：Ugwu et al. [2] 指出 AIFSN 對差異的影響最大，Mammeri et al. [3] 提出的 SDMA 需要通道綁定，不適用我們的單通道 BSS。

---

### 投影片 2-2：問題定義 `[CORE]`
**On slide：**
- 飢餓判據（偵測器）：
$$\text{Starv}(AC_i) \iff \Big(\tfrac{Q_i}{Q_{cap}} > Q_{th}\Big) \lor \big(P_{loss,i} > P_{th}\big),\quad Q_{th}=0.8,\ P_{th}=0.1$$
- 兩個指標互補，用 OR：佔用率＝持續被擠 · 丟包＝封包排不進來
- 靜態為何不夠：存取機率 $\tau \approx \tfrac{2}{\text{CWmin}+1}$ → VO 0.5 vs BE 0.125
- 一個陷阱（§4 會回來）：緩解飢餓會把佇列排空，等於消掉自己的觸發條件

**Say (~50s)：**
> 接下來把飢餓定義成可以判斷的條件：某個 AC 只要佇列佔用超過 80%，或丟包率超過 10%，就算飢餓。用這兩個是因為它們互補——佇列滿代表持續被擠，丟包高代表封包根本排不進來，所以用 OR 連起來。為什麼靜態一定不夠？因為存取機率大概是 2 除以 CWmin 加 1，VO 大概 0.5、BE 只有 0.125，而且沒有任何回饋去修正它。最後一個重點先講在前面：任何回饋控制只要成功緩解了飢餓，就會把它在看的佇列排空，等於把自己的觸發條件消掉，這在第四部分會再回來談。

# Part 3 — Solution：演算法虛擬碼 + 高階數學 · `[CORE]` · 預算 3:30

### 投影片 3-1：架構 `[CORE]`
**On slide：**
```
┌──────────────── QAD-EDCA Manager（在 AP）────────────────┐
│  監控 ──→  偵測 ──→  調整 ──→  回復                       │
│ 佇列/丟包  飢餓?   AIFSN/CW/TXOP  指數衰減               │
└──────────────────────────────────────────────────────────┘
       每 T_mon = 100 ms 一個控制迴圈 · 只調 AP 端
```
- AP 本來就會在 beacon 廣播 EDCA Parameter Set → 站台不用改
- 實作：INET `Hcf→Edca→Edcaf→TxopProcedure` 子類化鏈

**Say (~25s)：**
> 整個系統就是在 AP 加一個 manager，把標準少掉的迴路補起來：監控、偵測、調整、回復，每 100 毫秒做一次。因為只動 AP，而 AP 本來就會在 beacon 廣播 EDCA 參數，所以 client 端完全不用改。

---

### 投影片 3-2：緩解策略——調三個參數，對應三個存取階段 `[IF TIME]`
**On slide：**
偵測到飢餓時，三個一起動：
1. 降 BE/BK 的 AIFSN（−1/週期，下限 2）→ 早一點競爭
2. 雙向調 CWmin：提高 VO/VI（×α，上限 15）、降低 BE/BK（÷α，下限 7）
3. 降 VO/VI 的 TXOP（×β，下限 0.5 ms）→ 早一點放掉通道

> AIFSN＝何時開始競爭 · CWmin＝退避多久 · TXOP＝搶到後佔用多久

**Say (~35s)：**
> 為什麼要調三個參數？因為通道存取剛好有三個階段。AIFSN 決定什麼時候開始競爭，我們把飢餓的類別調短。CWmin 決定退避多久，這邊雙向調，VO/VI 調高、BE/BK 調低，但都設了上下限不會互相超過，所以優先順序還是保持住。TXOP 是搶到之後佔用多久，我們把 VO/VI 調短，讓它早點把通道放掉。

---

### 投影片 3-3：回復 · 安全閥 · 遲滯 `[IF TIME]`
**On slide：**
- 指數衰減回復（沒飢餓時）：$P \leftarrow P + \gamma(P_{def}-P)$，$\gamma=0.3$
- QoS 安全閥：若 $d_{VO}$ 或 $d_{VI} > 150$ ms → 往回拉一半，QoS 優先
- Schmitt 遲滯：門檻觸發、掉到 0.4× 以下才解除，避免一直開開關關

**Say (~30s)：**
> 另外有三個機制保證穩定。第一，沒有飢餓的時候參數是指數衰減慢慢調回去，不會一下跳回來造成震盪。第二，安全閥，只要 VO 或 VI 延遲超過 150 毫秒，就把調整往回拉一半，QoS 優先。第三，用 Schmitt 遲滯，門檻觸發但要掉到比較低才解除，避免短暫波動讓它一直開開關關。

---

### 投影片 3-4：演算法 + 數學 `[CORE]`
**On slide：**
```
每 T_mon（=100 ms，與 beacon 同步），在 AP：
  1. 對 i ∈ {BE,BK} 讀 Q_i/Q_cap 與 P_loss_i
  2. if Starv(BE) ∨ Starv(BK):                    // 三維調整
        AIFSN_{BE,BK} = max(AIFSN−1, 2)
        CWmin_{VO,VI} = min(CWmin·α, 15)           // 抑制高優先
        CWmin_{BE,BK} = max(CWmin/α, 7)            // 加速低優先
        TXOP_{VO,VI}  = max(TXOP·β, TXOP_min)
     else:                                         // 指數衰減回復
        P ← P + γ·(P_default − P)
  3. 經 beacon 廣播新的 EDCA set
  4. if d_VO>150ms ∨ d_VI>150ms:  P ← (P+P_default)/2   // QoS 安全閥
```
- 數學依據：$\tau \approx \tfrac{2}{\text{CWmin}+1}$，CWmin 3→15 使存取機率 0.5 → 0.125
- 複雜度 O(1)：每週期讀 4 佇列 + 4 丟包 + 門檻判斷，不用訓練（對比 DRL 的 O(推論)）

**Say (~50s)：**
> 這頁是完整的演算法。每 100 毫秒讀八個數字，如果 BE 或 BK 有飢餓，就做剛剛那三個調整；沒有的話就把參數衰減回預設。然後透過 beacon 廣播出去，最後再過一次 QoS 安全閥。數學的部分就是這條存取機率：把 CWmin 從 3 拉到 15，機率會從 0.5 降到 0.125，這就是我們抑制高優先的依據。複雜度是 O(1)，每次就是幾個讀取跟比較，不用訓練，這也是跟 DRL 那類方法最大的差別。

## Q&A 準備（~5 分鐘）

**Q1：QAD 穩態還是贏不過 Tuned Static，那價值在哪？**
> Tuned 是手動調好、而且假設已經知道負載、不會再變的設定。QAD 在不用調參、會自動跟著負載走的情況下，到它 6% 以內，而且把標準的飢餓吞吐拉到兩倍。我們也證明了在飽和穩態下，純回饋控制本來就贏不過調好的靜態，差距在每個 mix、每個規模都穩定，所以這是結構性的結果，不是沒調好。

**Q2：怎麼確定 QAD 在負載下真的有自適應？**
> 我們用 vector 記錄了 `starvationDetected` 跟調整後的 AIFSN、CWmin，重載下會觸發、參數會隨時間變動（`fig_dynamic_qad_adapt`）。第四部分的動態場景也可以看到它隨著 calm、surge、calm 在跟著負載走。

**Q3：為什麼不直接用 DRL（像 PDCF-DRL [6]）？**
> DRL 效能上界比較高，但要訓練幾千個 episode、需要算力，收斂前還可能比標準差，資源有限的 AP 不一定吃得消。QAD 是 O(1)、不用訓練，從第一個週期就有作用，甚至可以在 DRL 還在訓練的時候先頂著。它跟我們設定不同，所以是當參考上界，不是同條件比較。

**Q4：100 ms 的監控間隔會不會太慢？**
> 跟 beacon 同步，不會多花額外開銷。掃描結果顯示 50 到 500 毫秒對穩態 BE 的影響都在 1% 以內。再快只是多花運算、也比較容易震盪。

**Q5：跨 AC 的 Jain index [9] 為什麼反而下降？**
> 因為把本來就第二高的 BE 再拉高，四個 AC 反而更不平均。Jain's index [9] 在這個情境不適合拿來看飢餓緩解，應該看 BE、BK 有沒有脫離飢餓，也就是吞吐有沒有回來、丟包有沒有下降（`fairness_index`）。

**Q6：跟真實環境差多少？**
> 我們是理想通道、beacon 即時傳播、server 是無線雙跳（這也造成第四部分提到的偵測限制，AP 只看得到下行佇列）。真實環境會有衰落跟干擾，未來可以結合 802.11ax [10] 的 TWT，偵測也改用空中時間。
